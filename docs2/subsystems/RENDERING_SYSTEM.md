# Система рендеринга Lost Vikings

## Обзор

Игра использует **VGA Mode 13h-подобный** режим с модификациями:
- Разрешение: **320×200** (фактически 344×240 в буфере)
- Цвета: **256 цветов** из палитры 262144 (18-bit RGB)
- Формат: **Planar 4-bit** (4 цветовые плоскости)
- Прокрутка: **Аппаратная** через VGA регистры

## Архитектура рендеринга

```
Главный цикл (sub_1797b)
  ↓
VGA Pixel Panning (byte_317ce)
  ↓
State Machine Dispatcher
  ↓ (word_303de = 2)
Анимация палитры (sub_10ffc)
  ↓
Прокрутка уровня
  ↓
redraw_tilemap() - Копирование тайлов
  ↓
draw_tile() - Рендеринг 8×8 тайла
  ↓
VGA Memory (0xA000:xxxx)
  ↓
SDL Wrapper → Современный экран
```

## Ключевые компоненты

### 1. VGA Pixel Panning (Аппаратная прокрутка)

**Функция**: `sub_1797b` (строка 15492)

```c
// Установка горизонтального сдвига пикселей
OUT(0x3C0, 0x33);           // VGA Attribute Controller
OUT(0x3C0, byte_317ce);     // Значение сдвига (0-7 пикселей)
```

**Назначение**: Плавная прокрутка без перерисовки всего экрана

### 2. Анимация палитры

**Функция**: `sub_10ffc` (строки 3167-3238)

**Возможности**:
- 8 независимых слотов анимации (0-7)
- Настраиваемая скорость (период в кадрах)
- Диапазон цветов для каждого слота
- Поддержка прямой и обратной анимации

**Использование**:
- Огонь, лава (быстрая анимация, оранжевые оттенки)
- Вода (медленная анимация, синие оттенки)
- Мигающие огни
- Телепорты и магические эффекты

**Конфигурация слота**:
```
DS:0x2584+BX - Период анимации (кадры)
DS:0x258C+BX - Текущий счётчик
DS:0x2594+BX - Начальный индекс цвета
DS:0x259C+BX - Конечный индекс цвета
```

### 3. Копирование прокрутки

**Функция**: `redraw_tilemap` (строки 94-203)

**4-блочная система**:
```
┌─────────────────┐
│ Блок 1 (main)   │ ← Основной видимый экран
├─────────────────┤
│ Блок 2          │ ← Дополнительная прокрутка
├─────────────────┤
│ Блок 3          │ ← Третья область
├─────────────────┤
│ Блок 4          │ ← Четвёртая область
└─────────────────┘
```

**Адреса конфигурации**:
```
DS:0x9315 - Исходный адрес
DS:0x9317 - Адрес блока 1
DS:0x9319 - Адрес блока 2
DS:0x931B - Адрес блока 3
DS:0x931D - Адрес блока 4
DS:0x9311-0x9314 - Высота каждого блока (строк)
```

**Производительность**: ~160 байт копирования за вызов

### 4. Рендеринг тайлов

**Функция**: `draw_tile` (строки 205-775, 570 строк!)

**Формат тайла**: 8×8 пикселей, 64 байта
```
Offset  Plane  Data
0x00    0      Строки 0-7 (16 байт)
0x10    1      Строки 0-7 (16 байт)
0x20    2      Строки 0-7 (16 байт)
0x30    3      Строки 0-7 (16 байт)
```

**4 режима рендеринга**:
1. **Нормальный** (SI & 0x30 == 0)
2. **Flip H** (SI & 0x30 == 0x10) - Горизонтальное отражение
3. **Flip V** (SI & 0x30 == 0x20) - Вертикальное отражение
4. **Flip H+V** (SI & 0x30 == 0x30) - Оба отражения

**Параметры в SI**:
- Биты 0-3: не используются
- Бит 4 (0x10): Flip горизонтальный
- Бит 5 (0x20): Flip вертикальный
- Биты 6-15 (0xFFC0): Адрес тайла

**Алгоритм**: 4 прохода (по одному на плоскость)
```c
OUT(0x3C4, 0x102);  // Плоскость 0
// Копировать 8 строк
OUT(0x3C4, 0x202);  // Плоскость 1
// Копировать 8 строк
OUT(0x3C4, 0x402);  // Плоскость 2
// Копировать 8 строк
OUT(0x3C4, 0x802);  // Плоскость 3
// Копировать 8 строк
```

## VGA Planar Mode детали

### Формат памяти

VGA Planar Mode использует 4 битовые плоскости:
```
Пиксель = Plane0[bit] | Plane1[bit]<<1 | Plane2[bit]<<2 | Plane3[bit]<<3
```

**Пример**: Пиксель со значением 13 (0b1101):
- Plane 0: бит = 1
- Plane 1: бит = 0
- Plane 2: бит = 1
- Plane 3: бит = 1

### VGA Порты

| Порт | Регистр | Назначение |
|------|---------|-----------|
| 0x3C0 | Attribute Controller | Pixel panning |
| 0x3C4 | Sequencer Address | Выбор регистра |
| 0x3C5 | Sequencer Data | Map Mask (выбор плоскостей) |
| 0x3C8 | DAC Write Index | Индекс цвета для записи |
| 0x3C9 | DAC Data | RGB данные (3 байта × 6 бит) |
| 0x3CE | Graphics Controller | Выбор регистра |
| 0x3CF | Graphics Data | Bit Mask и др. |

### Адресация видеопамяти

**Базовый адрес**: 0xA000:0000

**Расчёт позиции пикселя** (X, Y):
```
offset = (Y * 86) + (X / 8)
plane = X % 8 через битовый доступ
```

**Шаг строки**: 86 байт = 344 пикселя / 4 плоскости

## Размеры экрана

| Параметр | Значение |
|----------|---------|
| Видимая область | 320×200 |
| Буфер рендеринга | 344×240 |
| Шаг строки | 86 байт |
| Байт на плоскость | 86 × 240 = 20640 |
| Всего VGA памяти | 20640 × 4 = 82560 байт |

## Оптимизации

1. **Двойная буферизация**: Через переключение начального адреса VGA
2. **Частичная перерисовка**: Только изменённые области
3. **Аппаратная прокрутка**: VGA pixel panning для плавности
4. **4 режима тайлов**: Экономия памяти (не нужно хранить отражённые версии)

## Производительность

**Типичный кадр**:
- Анимация палитры: ~8 слотов × 16 цветов = 128 цветов
- Прокрутка: ~160 байт копирования
- Тайлы: ~100 тайлов × 32 записи = 3200 операций

**Частота**: 60 FPS (каждые ~15ms)

## Связанные функции

### Документированные
- `sub_1797b` - Главный цикл
- `sub_10ffc` - Анимация палитры
- `redraw_tilemap` - Копирование прокрутки

### Требуют анализа

- Рендеринг UI и текста
- Эффекты (взрывы, телепорты и т.д.)

## Примечания

- SDL обёртки (`drawPixel`, `setPalette`) синхронизируют с современным рендерингом
- Код оптимизирован для 286/386 процессоров
- Используется прямой доступ к портам ввода-вывода (IN/OUT)
- Всё в реальном режиме DOS (real mode, segment:offset адресация)

## Презентер: FILTER < NONE | NEAREST | SHARP | LINEAR | XBRZ | HQX > (UX этап 9 шаг 3 + этап 11 хвост, 2026-09-10)

`v2_present_frame` (render_v2.cpp) кладёт кадр 320×240 (384/426 в широком режиме) в окно с
сохранением пропорций. Коды cfg `filter=`: 0 NEAREST (ближайший сосед SDL), 1 SHARP (целое k
ближайшим соседом в промежуточную текстуру, затем линейно до окна), 2 LINEAR, 3 XBRZ, 4 HQX,
5 NONE; меню F1 ходит в порядке NONE → NEAREST → SHARP → LINEAR → XBRZ → HQX.
- NONE — растр 1:1 по центру окна, без масштабирования (пиксельно точный вид, маленькие окна).
- XBRZ — xBRZ 1.8 (Zenju, GPL-3 с исключением MAME; `src/sdl/third_party/xbrz`, копия из PPSSPP без
  их заголовка конфигурации): кадр после палитры переводится из RGBA8888 (левые PW колонок буфера
  шириной RENDER_WIDTH_V2) в 0xAARRGGBB и масштабируется целым k = ⌊масштаб окна⌋ в пределах 2–6
  ломтями строк на min(ядра, 8, H/16) потоках `std::thread`; результат — текстура ARGB8888 PW·k×H·k
  с линейной выборкой, растянутая до окна (при точном k — без растяжки). 1280×960 (k=4): презентер
  держит 60 вызовов/с.
- HQX — hqx (Maxim Stepin/Cameron Zemek, LGPL-2.1; `src/sdl/third_party/hqx`), hq2x/3x/4x по k в
  пределах 2–4; таблица RGB→YUV ужата с 64 МБ (24-битный индекс) до 128 КБ (RGB555) — она питает
  только пороговые сравнения (Y 0x30, U 7, V 6), интерполяция идёт по полным цветам (NOTES.txt).
- GLOW-бордюр, INT.SCALE, широкий экран и `V2_PRESENT_SHOT` работают со всеми режимами; текст HUD
  и диалогов сглаживается наравне с графикой (свойство фильтров). Игровое состояние не
  затрагивается, SHARP по умолчанию (с 2026-09-10; до того NEAREST), канон без изменений. Проверено снимками уровня 1 при
  1280×960 (NEAREST / XBRZ / HQX) и титула при NONE.


## Презентер: vsync-lock и SMOOTH по подкадрам (2026-09-11; заменяет модель этапа 9)

**Факт, установленный на DOSBox-стенде и по логу флипов:** оригинал двигает камеру и спрайты
на КАЖДОМ vsync (Mode X 320×240 = 60 Гц). Игровой кадр = три подкадра render1/render2/render3
с разными позициями: позиция объекта (`OBJ_WORLD_X/Y`) шагает раз в тик, саб-спрайты догоняют
её третями (`OBJ_SPRITE_Y` 180→177→175 при объекте 193), вьюпорт скроллится каждый подкадр
(118→115→113). Запись DOSBox (mapper с F8 = захват AVI, zmbv 320×240, ~60 к/с): камера 1–3 px
и Эрик 1–2 px на кадр 60 Гц — движение оригинала гладкое само по себе.

**Что было не так.** Ожидание vsync игры (`v2_tick_sleep` в зеркале sub_10130) шло по таймеру
`SDL_Delay(16)` (фактически 16.3 мс), а презентер — по vsync дисплея (16.67 мс): часы бились,
раз в ~0.9 с подкадр показывался дважды, а следующий пропадал — тот рывок, ради которого этап 9
ввёл интерполяцию между ТИКАМИ. Она прятала биение, но выбрасывала родные подкадры, добавляла
игровой кадр задержки и дрожание ±1 px (камера и спрайт округлялись порознь).

**Сейчас.** `render_v2.cpp`: после каждого `SDL_RenderPresent` (блокируется на vsync) презентер
выдаёт игре «vsync» по сетке 60 Гц на обновлениях дисплея (60 Гц — каждое, 120 — каждое второе,
144 — 2/3/2/…; кратные 60 — точным делителем, прочие — измеренным отношением), игровой поток
блокируется на нём (`v2_vsync_wait_game`, отставание не навёрстывается — как опрос ретрейса в
DOS), а презентер защёлкивает новейший флип как можно позже перед следующим present
(`v2_vsync_latch_sleep`, ~3 мс до обновления): каждый подкадр показывается ровно один раз, одно
обновление задержки, как у страничного флипа VGA. Лок встаёт после прогрева в 32 present-а
(интервал должен устояться); без блокирующего present (V2_NO_PRESENT_VSYNC, dummy-драйвер,
композитор без vsync) игра держит собственный таймер 60.0 Гц с бегущим дедлайном. Проверено под
Xvfb: 2370 из 2371 интервалов флипов ровно одно обновление, 3 подкадра на игровой кадр.

**SMOOTH < NONE | AUTO | ON >** (`v2_smooth.cpp`, cfg `smooth=0/1/2`, по умолчанию AUTO;
старое `smooth=1` = «вкл» читается как AUTO). Интерполяция теперь между двумя новейшими
ФЛИПАМИ (подкадрами, 6–40 мс друг от друга; флипы ближе 4 мс — один подкадр, побеждает поздний):
камера и активные в обоих флипах саб-спрайты сдвигаются назад на (1−t) от своего шага, округление
одно, относительно точной камеры (`x = cam_i + round(x_f − cam_f)`) — викинг под захватом камеры
стоит на экране неподвижно, дрожания нет. AUTO включает её только когда лок стоит и частота
дисплея не кратна 60 (75/90/144/165 Гц: сетка 60 Гц там неровная — подкадр держится 2 или 3
обновления); на 60/120 Гц интерполировать нечего, и AUTO выключен. ON — всегда (ценой одного
подкадра задержки). Пункт меню показывает решение AUTO и частоту лока (`< AUTO > OFF 60 HZ`).

**Список команд (display list, 2026-09-11).** Презентер не решает, какие спрайты рисовать и в
каком порядке. Слои композиции флипа записывают каждую команду в `v2_frame_draws`
(`render_v2.h` V2DrawList: слот, флаги, мировая позиция, сегмент/смещение спрайта, число
полос, слой): ранний слой — все активные объекты в точке sub_1DE05, поздний — ровно те объекты,
которые диспетчеризовало зеркало sub_1DD9C (оно сообщает их через `v2_late_list_begin/add`, и
`v2_draw_sprites_late` рисует этот список вместо повторного вывода гейтов из состояния после
прохода). Снапшот флипа несёт список, презентер повторяет его командой за командой
(`v2_draw_list`), сдвинув каждую на долю шага её слота между двумя флипами; при t = 1 кадр
равен флипу байт в байт. Причина: поздний набор — функция прохода, а не состояния после него
(счётчик [114D], дошедший до 0 в проходе; force, сброшенный проходом), и прежний вывод из
снапшота ставил кнопку-подсказку поверх стоящего на ней викинга (уровень 2, кнопка (928,200):
у кнопки на флипе [114D]=1, у Эрика уже 0 — 77 из 755 флипов). Стенд «презентер == флип»:
`V2_SMOOTH_SELFTEST=<dir>:<from>-<to>` собирает композицию презентера при t = 1 на игровом
потоке при каждом флипе и пишет `sm_<n>_f<кадр>.ppm` рядом с `flip_*.ppm` V2_FLIP_DUMP
(0 расхождений на 1086 флипах четырёх реплеев после правки); строки
`V2-SMOOTH-SELFTEST-TIME` дают стоимость одной композиции (0,6 мс в среднем при -O0).

**Постраничные списки (page lists, 2026-09-11).** Кадр флипа — не «все активные объекты», а
то, что лежит на показываемой странице VGA оригинала. Для каждой из трёх страниц (роли 0 / 0x34
/ 0x68, слова ds:92F7/92F9/92FB) ведётся свой список команд рисования (`g_page_list` в
`v2_render_funcs.cpp`, API в `render_v2.h`) плюс карта эпох стирания по клеткам карты рендера
(`g_cell_epoch`, индекс — слово fs клетки: LUT_ROW[row] + col, как считают зеркала). Оригинал
стирает клетками, а не объектами: проход 1 sub_1DE05 лишь помечает OLD-прямоугольник объекта с
[114E] ≠ 0 (fs OR 3), обработчики спрайтов помечают свои клетки при рисовании, sub_1E16D —
клетки глифов, а проход 2 следующего sub_1DE05 копирует фон поверх КАЖДОЙ клетки окна с битом 0
на странице [92F7] (бит 0 снимает sub_1C8F1 в конце прохода). Поэтому смена кадра спрайта при
отставшей защёлке OLD оставляет пиксели прежнего кадра под новым (attract, объект 0x60: кадр
1201→1321, стёрт прямоугольник (256,288) вместо (256,272) — «искра» держится на одной странице
ещё кадр), объект, нарисованный без счётчика стирания, остаётся где был, окно текста стирает
спрайты под собой, а скан их перерисовывает — всё поклеточно. Списки меняют только зеркала,
ровно там, где оригинал меняет пиксели страницы: проход 2 sub_1DE05 (каждый восстановленный
спан на [92F7]) → `v2_page_list_erase_cells(page, fs, n)` — эпоха клеток растёт, команда,
нарисованная раньше, теряет эти клетки; sub_1DD9C (каждый диспетчеризованный объект рисуется на
[92F9]) → `v2_page_list_draw(page, cmd)` — команда добавляется в конец со своей эпохой, прежние
команды слота остаются, пока живы их клетки (их уцелевшие пиксели и есть остаток оригинала); запись
идёт ПОСЛЕ диспетчеризации обработчика, по его отчёту (`g_draw_clip`): объект, отсечённый гейтами
окна целиком (за экраном; оригинал диспетчеризует его каждый проход с [114D]=2, не рисуя), не
записывается, а частично отсечённый несёт маску столбцов обработчика (таблицы cs:1379/138B для
типа 2, cs:0E92/0E9A для типа 4, байт своей стороны при hflip) и число пропущенных полос сверху и
снизу (`mand`, `clip_top`, `clip_bot`), и растеризатор применяет их ровно как движки jpt_1DA02 /
jpt_1D514 (AND на маску полосы, пропуск полос); команда, идентичная уже лежащей на странице (слот,
позиция, спрайт, флаги, клип), заменяет её — новая накрывает каждый пиксель старой, а список
ограничивается числом различных образов (статичный объект, который скан перерисовывает каждый
проход, иначе заполнял бы 256 записей);
sub_16DC1/sub_16DD9 (ряд/столбец тайлов при скролле и полная заливка sub_11439 — на странице
рисования и копиями sub_171DC/sub_1712B на двух других) → `v2_page_lists_erase_cells_all` и
слово тайла клетки на всех трёх страницах; sub_1406d (квадранты анимированных тайлов на [92F9]
и [92FB]) → стирание клетки и её слово на той странице; sub_16880 (очистка VGA на смене уровня)
→ `v2_page_lists_black()`: все клетки чёрные, списки пусты. Тайлы — тоже состояние страницы
(`g_page_tile`: слово, нарисованное в клетке последним; 0xFFFF — слово карты на момент
композиции, 0xFFFE — чёрное): страница может держать старый кадр анимированного тайла (проход 2
копирует клетку из BG-страницы, а та не перерисовывалась) — level5: «капля» на стене на
странице 68 при карте уже без капли. Копирование клеток между страницами — `v2_page_cells_copy`:
проход 2 sub_1DE05 (BG → [92F7]) и часть 2 sub_1DF6A (ротация: [92F9] → новая BG [92FB] в
клетках с битом 1) — клетки назначения умирают, слова тайлов переносятся, а команды источника с
живыми пикселями в спане копируются с маской `keep` только этих клеток (так «запечённый» в фон
спрайт едет дальше, как на VGA). Копии одного прохода — один пакет (`_begin`/`_span`/`_end`):
одна копия на команду источника со всеми её живыми клетками во всех спанах прохода, а не копия
на каждый спан (иначе списки переполнялись: 1024 записей, арена исчерпана — «мусорное» яблоко
level7); прежняя копия того же образа, чьи клетки все скопированы заново, снимается. Дедупликация
записей сравнивает и БАЙТЫ полос: спрайт, чьи кадры пишутся в один и тот же слот банка (тот же
сегмент:смещение, новые данные — облачко дыма), оставляет прежний кадр под новым там, где новый
прозрачен, и его запись остаётся. Глифы — тоже команды: sub_1E0C7 рисует клетку текста в клетке
КАРТЫ (col + [257F], row + [2581]) на [92F9] → `v2_page_list_glyph` (тип V2_CMD_GLYPH, позиция
клетки в мире, индекс глифа); композиция рисует их после приоритетных тайлов, как проход (1E0C7
идёт после 1C8F1), и на экране они стоят в клетке карты минус камера — фаза тонкого скролла
0..7 px сама собой; `v2_draw_ui` при этом рисует только CJK-оверлей. Пиксели команды — байты
полос спрайта НА МОМЕНТ РИСОВАНИЯ: страница хранит нарисованное, а банки спрайтов под ней
перезаливаются (смена уровня/сцены заполняет сегменты, пока старые страницы ещё показываются —
викинги меняли позу, level4 f3359 давал мусор), поэтому каждая запись несёт копию своих полос в
арене списка (`V2DrawList::arena`, 768 КБ; тип 1 — 72 байта, тип 4 — 288, тип 2 — 36 × полос,
глиф — 72), растеризатор читает копию, копии спанов переносят байты, `v2_page_list_bake`
уплотняет арену, списки копируются `v2_drawlist_copy` (записи + занятая часть арены). Цикл
sub_104a1 (окно пароля / переходный текст / QUIT TO DOS) больше не компонует и не публикует
кадр на каждой итерации (это делало зеркало `v2_pw_iter_body` — окно без фазы, объекты, не
нарисованные проходами, приоритетные тайлы первого кадра): флипы идут только из зеркала
sub_16775 до цикла и в ветке мигания sub_10555, как в оригинале. Композиция флипа делается в одном
месте — в зеркале sub_16775 перед публикацией (`v2_compose_page`: тайлы карты у камеры или
картинка чанка; `v2_page_list_bake` — маска мёртвых клеток каждой команды показываемой страницы
[92F9] относительно её левого верхнего угла (8 столбцов × 32 ряда) и снятие команд без живых
клеток; команды в их порядке, растеризатор пропускает пиксели мёртвых клеток; приоритетные
тайлы; UI; флаг `v2_compose_at_flip` пропускает слои через гейт `v2_vm_in_frame`, потому что
флипы блокирующих циклов идут вне кадра) — в обеих сборках, и этот же список становится
`v2_frame_draws` снапшота для презентера (маска едет вместе со спрайтом при интерполяции;
интерполируется только последняя команда слота, остатки стоят на месте). Что это закрывает по
построению: блокирующие циклы (окно пароля на старте уровня: loc_10169 после sub_104a1 трижды
флипает страницы как есть, без проходов — теперь и кадр игры показывает страницу, а не свежую
композицию каждой итерации: «бомба» 4A, порождённая с [114D]=0 и не рисованная оригиналом до
force/скана, отсутствует, пока окно открыто; Олаф за колонной приоритетных тайлов), 1–2-флиповые
появления и остатки, клипы на краях окна, первые флипы смены уровня и страницы после force.

игры показывает из страницы): attract, empty, level2, level5, synth_inventory, synth_pw_enter,

дампами теневой VGA и реального drawBuffer порта (V2_VGA_DUMP, intro f3531, флип n=75 — флип
sub_11439 сразу после заливки sub_16DED): порядок событий sub_16880 (очистка) → 25 рядов
sub_16DC1 → флип; окно CRTC этого флипа начинается со строки VGA 577 (crtc C208, страница 34),
а нарисованные заливкой строки VGA кончаются на 696 — строки окна 119..175 читают
незакрашенные строки (0x00 после очистки) в ОБОИХ буферах, теневом и реальном, то есть это
поведение оригинала: страницы — не ряды клеток карты, а линейная память VGA (строки каждой
страницы лежат с фазой 42 байта внутри шага 0x56; ряд тайлов рисуется по LUT_PAGE_ROW[ряд] +
столбцовое слагаемое, а окно — это 80 байт на строку, читаемые линейно от CRTC-старта
sub_16775 = LUT_SUBROW + LUT_PAGE_ROW + (x >> 2) + 8, поперёк границ шага и по кольцу), и первый
флип уровня показывает ряды заливки там, где она их положила, а ниже — незалитые 0x00.
И не только незалитые нули: там, куда полуочистка порта sub_16880 (0x8001 байт) не дошла, лежат
пиксели прошлой сцены (chunk-картинка intro 2C, индекс 0x20) или прошлого уровня (его тайлы —
под уже НОВОЙ графикой тайлов, level6). Закрыто ФОНОВОЙ VGA (2026-09-12): вторая пиксельная
плоскость теневой VGA `v2_vga_bg`, в которую попадают только фоновые писатели — тайловый
рисователь (зеркало sub_1689E) и картинки-чанки sub_10cd8 (флаг `v2_vga_bg_writer` вокруг них,
проверка в `v2_vga_w`), плюс копии спанов и заливки (`v2_vga_copy_span`/`v2_vga_fill_span`
всегда зеркалят), и никогда — движки спрайтов, глифы и перерисовка приоритетных тайлов (они
остаются командами поверх). Перерисовка приоритетного тайла sub_1C8F1 (грязная клетка с битом 3,
масочный тайл переднего плана поверх спрайта) с этого момента — тоже команда списка
(`v2_page_list_fgtile`, тип V2_CMD_FGTILE: одна клетка карты в мировых координатах и слово тайла
после подстановки, обязательная, снимается стиранием своей клетки, как остальные), а не
сплошной проход по всем флаговым клеткам окна поверх готового кадра: сплошной проход перекрывал
чтение фоновой VGA там, где страница тайла ещё не несла (те же незалитые ряды первого флипа —
последние 2 расходящиеся строки на старт уровня). Композиция без консольного параллакса рисует
список одним проходом в порядке страниц (`v2_draw_list(..., -1)`: спрайты, перерисовки и глифы
вперемешку, как их клали проходы оригинала; `v2_tls_fg_from_page` выключает сплошной проход);
с параллаксом остаётся порядок спрайты → сплошной приоритетный проход → глифы, потому что
слою параллакса нужен приоритетный слой целиком. Слой тайлов композиции — чтение окна из неё побайтно, как делает
CRTC (`v2_vga_bg_readout`: байт crtc + y·0x56 + ((pan + x) >> 2), плоскость (pan + x) & 3, с
переносом счётчика адреса через 64 КБ), по 320 центральным столбцам поверх поклеточного прохода
по карте, который остаётся для крыльев широкого кадра; индекс 0 прозрачен над параллаксом.
Презентер несёт копию фоновой VGA в снапшоте и считает CRTC-старт для своей интерполированной
камеры той же формулой (`v2_crtc_for_camera` по DS снапшота). Попутно снята прежняя попытка
«владельцы строк VGA» (ключ addr/0x56 неверен при фазе 42) и промежуточная «символьная VGA»
(слова тайлов не выражают застойных пикселей). Палитра в этот флип всё равно чёрная (fade) —
на экране ничего не меняется, но индексы теперь равны странице. Окна текста, окно пароля
TLPT, QUIT TO DOS, сцены вступления 2B/2C, «капля» level5, «искра» attract, «яблоко» level7 —
равны странице. Chunk-экраны (byte_2AAAF & 0x42: логотипы, титул с CRTC-скроллом к
логотипу и меню поверх, окно пароля) сборка игры показывает из теневой VGA-модели страницы
(гейт V2_ONLY в `v2_vga_w` снят; `v2_swap_render_buf`: окно через CRTC зеркала sub_16775,
полоса HUD из строк VGA 0..63, DAC как есть, CJK-оверлей поверх) — тот же кадр, что DOS. Отладка: `V2_PAGELIST_TRACE=<слот hex>` — строки
`V2-PL`: события draw/bake/clear слота, его запись при композиции и поля DS ([114D]/[114E],
CUR/OLD, смещение спрайта, слова страниц) в точках 1DE05, 1DD9C (с причиной гейта или «out») и
флипа; `V2_PL_ERASE_TRACE=<от>-<до>` — строки `V2-PLE`: каждое стирание клеток в диапазоне
кадров с именем писателя (1DE05p2, 16DC1, 16DD9, 1406d), страницей, смещением fs и эпохой.

Дампы: `V2_SMOOTH_DUMP=<dir>` пишет `flip_log.txt` (каждый флип игрового потока: кадр, время,
вьюпорт, объект и первый саб-спрайт активного викинга — по нему и виден подкадровый ход
оригинала) и `smooth_log.txt` (только когда интерполяция активна: t, период пары, камера и
позиции prev/cur/lerp).

Экраны-картинки (byte_2AAAF & 0x42: логотипы-чанки, титул, меню, пароль) презентер не собирает
никогда — снапшот флипа считается тайловым кадром только если последний `v2_draw_tiles` шёл
тайловым путём И уровень флипа не экран-картинка (правило sub_11439, 2026-09-11). Один флаг
`v2_last_frame_tiles` устаревал на смене уровня: флипы fade-in титула (его игровой цикл ещё не
звал `v2_draw_tiles`) несли флаг тайлового уровня S&S, презентер собирал их сам, путь
экрана-картинки в презентерском режиме выходит не рисуя, и буфер презентера показывал последнее
собранное — логотип S&S под палитрой титула («грязный буфер» при загрузке).

Диагностика показов и флипов: `V2_PRESENT_DUMP=<dir>:<from>-<to>` пишет КАЖДЫЙ показанный кадр
в диапазоне игровых кадров (`pf_<n>_f<кадр>_<мс>_<sm|tick<причина>>.ppm` — холст 320×240
презентера: собранный им кадр (sm) или флип игры (tick)); `V2_FLIP_DUMP=<dir>:<from>-<to>` пишет
кадр каждого флипа (`flip_<n>_f<кадр>.ppm`: строки карты буфера показа + полоса HUD, через только
что опубликованный DAC) — в сборке игры это буфер композиции, в test mode страница теневого VGA,
которую сравнивает судья; последовательности флипов двух сборок одного реплея кладутся рядом.
В test mode рядом с каждым `flip_*.ppm` пишется `lin_*.ppm` — линейная композиция того же
флипа (то, что показывает сборка игры), и `V2_LINCMP=1` сравнивает её со страницей на каждом
флипе (строка `V2-LINCMP f<кадр> diff=<px> bbox=... lvl=... flags=... pairs(page:lin) a:b=n ...` —
пары индексов страница:композиция самых частых расхождений; сводка при выходе). Сравниваются
ИНДЕКСЫ, не цвета: на затемнённой палитре (fade старта уровня) расхождение может быть невидимым,
а дампы `flip_/lin_` (через DAC) при этом равны. Chunk-экраны (флаги 0x42) не сравниваются —
их сборка игры тоже показывает из страницы.
