# Анализ слепых зон верификации и механизмы их закрытия

Повод: дивергенции №49 (pause-меню, V2_ONLY-копия 11cbb) и №50 (vsync-вызовы
в 115d2) прожили все существующие каналы (fn-test 424 юнита, vmops, PSNAP,
DS-hash, shadow-VGA/A2, 13 сценариев, branch-coverage #60) и были найдены
только построчной сверкой кода в фазе C. Этот документ классифицирует, ПОЧЕМУ
каналы слепы к таким классам, и предлагает конкретные механизмы ловли.

## 1. Классификация слепых зон

Вся действующая верификация — **сравнение состояний** (DS-байты, shadow-VGA,
FS, снапшоты в точках). Она принципиально не видит четыре класса:

### Класс A: эффекты вне сравниваемого состояния
Вызовы, не оставляющие следа в DS/VGA: SFX (`sub_177bb` SDL-замещена в ОБЕИХ
сторонах — вызов не пишет DS ни в оракуле, ни в v2), ожидания
(`sub_10130` только читает-ждёт `[A39C]`). Юнит-оракул сравнивает DS-образы —
они совпадают при пропущенном/лишнем вызове.

### Класс B: пути без orig-пары (V2_ONLY-only код)
Живое сравнение (SFX-аудит, VGAPARITY, DS-hash per-op) существует только в
default-режиме, где исполняются оба мира. Код, достижимый только в V2_ONLY
(вторая копия pause-логики), не имеет партнёра для сравнения вообще.

### Класс C: дубли реализаций
Одна orig-процедура — несколько v2-воплощений (default-зеркало + V2_ONLY-
копия + fn-test-зеркало: у 11cbb их было ТРИ, у 117AD — два). Фикс и юнит
попадают в одну копию; остальные продолжают дивергировать. №44 фиксилась в
79xx-копии, 21529-копия осталась урезанной (=№49).

### Класс D: документированные async-исключения
`0xA39C` (vsync counter) легально в `v2_ds_hash_skip` и вне watch — race by
design. Всё, что проявляется ТОЛЬКО через исключённое слово (какой вызов и
сколько раз его ждал), невидимо. Сумма вызовов 10130 в 115d2 случайно
сходилась (дубль SF2 маскировал пропуски SF3/SF4) — баланс флипов не «вис».

## 2. Механизмы ловли (по классам)

### M1. Call-parity канал (классы A, D) — САМЫЙ ДЕШЁВЫЙ/МОЩНЫЙ
Пер-функциональные счётчики вызовов, сравниваемые на границах фаз (PSNAP-
точки уже есть):
- orig-сторона: инкремент в m2c-вставке на входе замещённых/зеркалируемых
  процедур (sub_10130, sub_16775, sub_177bb, sub_1183d, sub_118ad, sub_120d1,
  sub_11f93, sub_121b9, sub_1de05, sub_1dd9c, sub_1c8f1 — весь список
  зеркал из V2_FUNCTION_NAMES.md);
- v2-сторона: инкремент в теле каждого v2-зеркала;
- сравнение: в v2_compare_phase_snap добавить сверку векторов счётчиков
  (счётчики вне DS — отдельный массив, нет конфликта с байт-верификацией).
№50 ловится мгновенно: orig 10130-счётчик за 115d2 = 4, v2 = 3.
№49-switch тоже: orig 1183d-счётчик ≠ v2 (лишний вызов), 118ad ≠ (нет трёх).
Стоимость: таблица ~30 счётчиков + макрос; вставки в orig — по образцу
существующих `{ v2_...(ds); }`-вставок.

### M2. Golden-трейс для V2_ONLY (классы A, B)
Детерминизм реплеев уже доказан (FRAMESUM-паритет, dedup-CRC). Расширение:
- default-прогон реплея пишет event-лог: SFX (seq, obj, frame, fire_idx —
  канал v2_audit уже вычисляет детерминированные handle-хэши), вызовы
  рендер-примитивов HUD (1183d/118ad: di, ax, frame);
- V2_ONLY-прогон того же реплея пишет свой лог;
- сравнение файлов = оффлайн-дифф. Ловит №49-SFX и №49-рендеры в V2_ONLY.
Инфраструктура: env V2_EVENT_TRACE=file + скрипт сравнения в scenarios.sh
(пары default↔V2_ONLY для сценариев, помеченных как «оба режима»).

### M3. Call-order audit — статическая сверка код-против-кода (все классы)
Автоматизация того, что фаза C делает вручную: для каждой пары
(orig sub_X ↔ v2-зеркало) извлечь:
- из orig-тела: последовательность `J(CALL(sub_*))`/`J(CALLF(...))`
  в порядке следования (+ JMP-tail);
- из v2-тела: последовательность вызовов `v2_*`-зеркал (маппинг имён из
  docs2/ref/V2_FUNCTION_NAMES.md);
- отчёт-дифф последовательностей (вставки/пропуски/перестановки).
Это НЕ доказательство эквивалентности (ветвления упрощены), но детектор
несоответствий уровня №49/№50: лишний 1183d, отсутствующий 120d1,
отсутствующие 10130 — все видны как дифф последовательностей.
Прототип: python, вход — оба .cpp + таблица имён; выход — отчёт по ~180
парам. Ложные срабатывания (легальные v2-перестройки) гасятся
whitelist-аннотациями в отчёте, НЕ в верификации.

### M4. Инвентаризация и дедупликация копий (класс C)
- Одноразовый аудит: скан v2-кода на «клоны» — фрагменты с совпадающим
  мультимножеством DS-констант/вызовов (сигнатурный хэш тела); отчёт пар.
  11cbb (три копии), 117AD (две), 120d1/121b9-инлайны — нашлись бы сразу.
- Правило процесса (уже применяю в фазе C): при фиксе дивергенции — grep
  ВСЕХ сайтов паттерна (по вызываемым функциям и DS-оффсетам), чек-лист
  копий в задаче фикса.
- Фаза C системно устраняет класс: каждая волна заменяет инлайны вызовами
  единственной экстракции (11f93/121b9/120d1/11f47 уже слиты).

### M5. Сценарное покрытие веток взаимодействия (класс B)
Ветки, достижимые только цепочкой действий (pause с ПРЕДМЕТОМ), не
покрываются ни юнитами (SDL-замещённые эффекты), ни короткими синтетиками.
- Добавлен `synth_pause_item` (TAB-меню: свитчи LCTRL, 4 стрелки + «в упор»
  для безусловного erase-old, F-pickup пустого слота, TAB-выход) — покрывает
  mode-1 ветки №49 живым прогоном.
- Mode-0 (Action/Exit С предметом) требует предмета в инвентаре: стартовый
  инвентарь level 1 пуст (сеется геймплеем). Нужна человеческая запись
  (tests/record.sh, план `inventory` в SCENARIOS.md) ЛИБО синтетический
  маршрут до ближайшего предмета уровня (исследование spawn-таблицы).
- Систематизация: для каждой blocking-loop функции (11cbb, 11c52, 10350,
  1041c...) — таблица веток × сценариев в SCENARIOS.md, дырки = план записи.

## 3. Приоритет внедрения
1. **M1 (call-parity)** — максимум ловли за минимум кода; закрывает A+D.
2. **M3 (call-order audit)** — статический, без прогонов; закрывает
   остатки фазы C заранее (отчёт до переписывания).
3. **M5** — synth_pause_item уже в наборе; записать `inventory` (человек).
4. **M2 (golden-трейс)** — после M1 (переиспользует его точки).
5. **M4-аудит** — разовый скрипт; правило grep-копий действует уже сейчас.

## 4. Ограничения честности
- M1/M2 не доказывают порядок внутри фазы — только счёт/множество; порядок
  доказывает M3 + PSNAP-точки между вызовами.
- M3 статически не видит условность вызова (ветка может легально не звать) —
  его диффы = кандидаты на ручную сверку, не вердикты.
- Класс D неустраним полностью: async-слова остаются async; M1 меряет
  ИНВАРИАНТЫ вокруг них (счёт вызовов), не сами значения.
