# Дорожная карта: полный перевод движка на высокоуровневый язык

Статус: предложение (2026-08). Конечная цель по решению юзера: **движок,
полностью переписанный на языке высокого уровня, с нормальными структурами
данных; формат и содержимое DATA.DAT разрешено менять.**

---

## 1. Что такое «движок» сейчас — инвентарь низкоуровневых слоёв

Текущий v2 (после teardown) — байт-точная реимплементация, но её сердце
всё ещё *интерпретирует оригинал*:

| # | Слой | Низкоуровневая суть | Объём |
|---|------|---------------------|-------|
| L1 | DS-состояние | плоский 64K-образ, типизирован на 100% (фаза D), но носитель байтовый | ~1400 view-сайтов, 521 ObjMem, 424+75 ds_read/write |
| L2 | VM объектов | интерпретатор 216 опкодов; поведение объектов = байткод из DATA.DAT | ~9K строк хендлеров + скрипты в данных |
| L3 | Anim-VM | интерпретатор 27 команд; анимации = байткод | скрипты в данных |
| L4 | DATA.DAT | ~535 LZSS-чанков: тайлы, спрайты, тайлмапы, палитры, скрипты (L2/L3-код!), XMID-музыка, таблицы уровней | 1.57 MB |
| L5 | Звук | 8086-интерпретатор ОРИГИНАЛЬНОГО драйвера SBPFM.ADV + Nuked OPL3 | v2_ail_interp |
| L6 | Рендер | Mode-X модель (3 страницы, CRTC, план-биты) поверх плоского буфера | render-слой |
| L7 | Тайминг | 3 vsync-пейджфлипа на кадр ≈ 53ms (18.9 fps DOS) | main loop |

Ключевой факт: **поведение игры живёт в данных** (L2/L3-скрипты внутри
DATA.DAT), а не в C++-коде. «Высокоуровневый движок» недостижим без
подъёма скриптов — иначе навсегда остаётся интерпретатор байткода и
байтоадресуемый DS (именно об это разбился «наивный» эндшпиль фазы D:
операндные ds_write, bulk-чанки).

## 2. Целевая архитектура

```
assets/                          # разобранный DATA.DAT (редактируемый)
  levels/NN/{tilemap.json, spawns.json, links.json}
  gfx/{tiles,sprites,ui}/*.png + atlas.json
  palettes/*.pal.json
  scripts/{objects,scenes}/*.lvs   # декомпилированные скрипты (DSL)
  anims/*.lva                      # декомпилированные анимации
  music/*.mid + timbres/*.json     # XMID→MIDI + FM-тембры банка
  text/*.json

engine/ (C++)
  state:   struct GameState { typed поля; объекты = struct Object[] }
  logic:   скомпилированные из DSL функции поведения (генерённый C++)
           ИЛИ рантайм DSL-исполнитель высокого уровня (решение в 5.3)
  render:  чистый 2D (кадр = композиция слоёв; Mode-X убран)
  audio:   XMID-секвенсор + OPL3 (Nuked) с тембрами из assets
  timing:  фиксированный логический степ 53ms (совместимый), рендер любой
```

Канон при этом ПЕРЕЕЗЖАЕТ с байтового на **поведенческий**: golden-снапшоты
уже сегодня сравниваются по именованным полям (`v2_gs_dump_text`) — это
готовый носитель эквивалентности, не привязанный к байтовому образу.

## 3. Мост между мирами: две аксиомы миграции

**А1. Ни один шаг не теряет оракула.** Каждая стадия имеет двусторонний
тест: старый путь и новый путь исполняют один реплей, состояние сверяется
(сначала байтово, позже — по typed-полям). Инфраструктура уже есть:
golden 58, roundtrip, save/load, trace-каналы, PSNAP-методика.

**А2. Данные поднимаются раньше кода.** Пока скрипты — байткод, DS обязан
быть байтоадресуемым. Поэтому порядок: сначала экстракция и *дизассемблер*
скриптов (получаем полную карту адресов → закрывает этап D роутером),
затем декомпиляция и транспиляция (убирает VM), и только потом смена
носителя состояния на свободные структуры.

## 4. Стадии

### Стадия 0 — фаза D: этапы A/B/C/E/F (уже согласованы)
Типизация всех константных/табличных/объектных/чанковых/AIL доступов.
Выход: единственные «сырые» клиенты DS — операндные ds_read/write
интерпретатора. Оракул: канон + юнит-сет, байтовый.

### Стадия 1 — инструменты данных (фундамент всего)
1.1 **Экстрактор DATA.DAT** → `assets_raw/`: все ~535 чанков, распакованные,
    с манифестом (id, размер, потребители по карте лоадеров). База есть
    (класс D читал весь файл байт-в-байт; python/extract_*).
1.2 **Дизассемблер L2/L3-байткода**: по нашей полной карте опкодов (мы
    знаем семантику всех 216+27 — она уже реализована в v2 хендлерами).
    Выход: листинги всех скриптов всех уровней + перекрёстный индекс.
1.3 **Статический анализ скриптов**: CFG, достижимые опкоды, полное
    множество DS-адресов, которых касаются операндные опы (закрывает
    этап D фазы D: генерённый роутер offset→typed-поле, доказанно
    тотальный на реальных данных), список object-классов и их шаринг
    между уровнями.
Оракул: раунд-трип экстракции (repack == оригинал байт-в-байт).

### Стадия 2 — декомпиляция скриптов в DSL
2.1 Структурная реконструкция: jump-сети → if/while/state-машины.
    Опкоды → примитивы DSL (`move`, `spawn`, `sfx`, `on_input`,
    `wait_frames`, `set_field(NAME)` — DS-адреса из 1.3 переводятся в
    ИМЕНА полей фазы D!).
2.2 Формат DSL (`.lvs`) — текстовый, редактируемый, версионируемый.
2.3 **Компилятор DSL→байткод**: первый большой канон-тест — компиляция
    декомпилята обязана дать байт-в-байт оригинальные скрипты (или
    семантически эквивалентные с доказательством по dual-run). Это
    двусторонняя проверка честности декомпилятора.
Оракул: repack DATA.DAT из декомпилята == оригинал; канон-реплеи зелёные.

### Стадия 3 — транспиляция: убираем VM
3.1 Генератор DSL→C++: каждый object-класс → нативная функция/структура
    (корутина/state-машина, состояние — typed-поля Stage-0).
3.2 **Dual-run верификация**: движок умеет исполнять объект ОБОИМИ путями
    (интерпретатор vs транспилят); на канон-реплеях после каждого
    VM-пасса состояния сравниваются. Переключение по-объектно
    (как когда-то опкоды «one-by-one»), пока интерпретатор не станет
    мёртвым кодом.
3.3 Интерпретатор и anim-VM удаляются (teardown-стилем).
Оракул: dual-run на 58+ реплеях, затем канон на чистом транспиляте.

### Стадия 4 — носитель состояния: свободные структуры
Все клиенты DS теперь типизированы (Stage 0) и статичны (Stage 3 — нет
вычисляемых адресов). View-слой перегенерируется на member-поля
`GameState`; сериализатор остаётся ТОЛЬКО для golden/save-совместимости.
Дальше форма свободна: массивы объектов как struct Object[], enum-ы,
bool-ы. Golden переезжает на поведенческий формат (те же имена полей).

### Стадия 5 — ресурсы в открытом формате
5.1 Конвертеры: тайлы/спрайты → PNG-атласы; тайлмапы → JSON; палитры,
    текст, таблицы — JSON; XMID → MIDI + тембры банка → JSON.
5.2 Движок читает assets/ напрямую; DATA.DAT больше не нужен рантайму
    (остаётся эталоном для регресс-конвертации, пока хочется).
5.3 Решение по логике: генерённый C++ (макс. скорость и «всё в компиляторе»)
    или高-уровневый DSL-рантайм (модифицируемость без пересборки) — можно
    оба: DSL — исходник, C++ — прекомпилят.

### Стадия 6 — подсистемы
6.1 Звук: XMID-секвенсор поверх OPL3 (Nuked остаётся звуковым «железом»,
    интерпретатор SBPFM.ADV умирает; тембры и канальная модель — из банка).
    Оракул: OPL-регистровый трейс на реплеях == интерпретаторный
    (V2_OPL_TRACE уже существует).
6.2 Рендер: убрать Mode-X (страницы/CRTC/панораму) — кадр строится
    напрямую; сплит-скрин/скролл — нормальными координатами.
    Оракул: попиксельное сравнение композиции на реплеях.
6.3 Тайминг: логический степ 53ms (геймплей канон), рендер-частота
    развязана (интерполяция — опционально, off по умолчанию).

## 5. Инвентарь неизвестных (что показал бы Stage-1 анализ)
- сколько УНИКАЛЬНЫХ object-скриптов (шаринг между уровнями);
- полный словарь реально используемых опкодов по скриптам (216 в таблице,
  исполняются десятки — остальные хендлеры станут мёртвыми после Stage 3);
- множество операндных DS-адресов (ожидание: небольшое, скалярные поля
  сцен — счётчики/флаги; проверяется генератором роутера);
- сцены (интро/меню/пароль) — те же скрипты: декомпилируются вместе.

## 6. Риски и их закрытие
- **Недекомпилируемый паттерн** (самомодификация, целочисленные трюки):
  ловится Stage-1 анализом; fallback — точечный ручной перевод (как VM
  опкоды «one-by-one»).
- **Дрейф семантики DSL**: закрыт двусторонним компилятором (Stage 2.3)
  и dual-run (Stage 3.2).
- **Поведенческий канон слабее байтового**: переезд канона происходит
  ПОСЛЕ Stage 3, когда байтовый и typed-мир совпадают по построению;
  golden-поля уже семантические.
- **Замена данных ломает канон**: пока живём на оригинальных данных,
  repack == оригинал; после Stage 5 канон = поведенческий на
  конвертированных данных, зафиксированный новым golden-набором.

## 7. Порядок работ (сводный)
```
Stage 0  (фаза D A/B/C/E/F)         — механика, конвейер готов
Stage 1  (extract + disasm + анализ) — DONE (534 чанка, walker 0/0,
         STRICT-входы; см. tools/data/)
Stage 0D (роутер операндных)         — после карты адресов из 1.3
Stage 2  (декомпилятор + DSL + компилятор-обратно) — DONE (.lvs/.lvsf
         байт-в-байт ×6, lvsc-авторинг доказан edit-proof-ом)
Stage 3  (транспилят + dual-run)     — DONE (обе VM генерируются,
         GENCODE-дефолт, канон 58/58 + монки 37/37; смерть петли и
         таблицы = задача #96 в конце B — см. STAGE3_PROPOSAL.md)
Stage B  (инлайн-пассы семантики хендлеров в ген-код) — СЛЕДУЮЩИЙ
Stage 4  (GameState как носитель)
Stage 5  (assets/ вместо DATA.DAT)
Stage 6  (звук/рендер/тайминг нативные)
```
Каждый пункт — отдельные серии с канон+сет; teardown-ветка получает
merge-ами.
