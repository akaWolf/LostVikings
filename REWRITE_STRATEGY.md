# Стратегия переписывания asm → C++ — анализ и выбранный путь

Вопрос: как вообще правильно переписывать рукописный DOS-asm (Lost Vikings) на
C++, и рационален ли подход с дифференциальными тестами (FN_TEST_ANALYSIS.md),
или существует лучшее решение.

---

## 1. Классы стратегий и где мы

Для рукописного DOS-asm существует пять путей:

| Путь | Верификация | Итог |
|---|---|---|
| **Эмуляция** (DOSBox-обёртка) | бесплатная, 100% | это не переписка — логика недоступна, нативного порта нет |
| **Статический транслят** (m2c) | исполняется 1:1 | «asm в синтаксисе C++», нечитаемо — у нас это фундамент, не результат |
| **Matching decompilation** (путь sm64/OoT decomp) | diff бинарей, абсолютная | **недоступен**: оригинал написан руками на asm, нет компилятора, который дал бы байт-в-байт |
| **Clean-room по спеке** | поведенческая (слабая) | неточности расползаются; для «100% identical» недостаточно строго |
| **Strangler-паттерн**: исполняемый эталон + инкрементальная замена функций + машинная сверка состояния | byte-exact DS/VGA каждую фазу кадра | **это v2 — выбранный путь** |

Выбранный путь — тот же, каким сделаны OpenRCT2, devilution (Diablo), OpenTTD.
Разница в нашу пользу: у них сверка была слабее (спот-чеки, save-совместимость,
ручное тестирование) — у нас byte-exact DS на каждой фазе кадра.

Поскольку matching decomp физически недоступен (нет компилятора-эталона),
**семантическая эквивалентность по состоянию памяти — максимум строгости,
достижимый для этой игры в принципе**. Стратегия выбрана верно; вопросы только
в тактике.

## 2. Четыре реальных слабости текущей тактики и их закрытие

**(а) Верификация живёт только в лок-степ прогоне.** Ошибка в функции
проявляется как дрейф состояния позже; отладка = бисекция кадров/фаз (PSNAP
улучшил, но не устранил); итерация = минуты полного replay. → Закрывается
fn-фикстурами (FN_TEST_ANALYSIS.md, Mode B: миллисекунды; чистый вход вместо
накопленного дрейфа локализует баг в самой функции).

**(б) Верификация умрёт вместе с orig-слоем — главный пункт.** Конечная цель —
выкинуть orig (myDrawInfo WILL BE REMOVED, v2 полностью независим). В момент
отрезания live-verify исчезает, и удерживать поведение будет нечем, кроме
end-to-end replay (медленно, грубая локализация). Фикстуры — единственный
артефакт, который переживает смерть эталона: голдены, снятые с orig, продолжают
проверять v2, когда orig уже нет. **Тесты — не дополнение к live-verify, а его
наследник.**

**(в) Всё стоит на аксиоме «m2c == DOS-оригинал».** M2C_PORT_DIFFERENCES.md
фиксирует, что порт местами отличается. Для строгого «100% identical to
original» рано или поздно обязателен выборочный аудит против настоящего DOS
(DOSBox-X debugger, дампы состояния по брейкпоинтам). Формат фикстур
source-агностичен (`meta.source = m2c-replay | dosbox`) именно под это.

**(г) Replay-корпус мал** (attract + intro ≈ 2–3 уровня из ~37). Дешёвое
расширение: по записи на уровень. Фикстуры наследуют покрытие корпуса
автоматически; fuzz (Tier 3, уже есть) добавляет хвосты.

## 3. Путь до «нормальных плюсов» (а не C++-транскрипции asm)

Сейчас v2 — «читаемый C++ поверх оригинального memory layout» (сырые офсеты
`s+0x372`). Это правильно для фазы сверки, но не конечная форма. Фазы:

- **Фаза A (текущая): паритет.** Никакого рефакторинга по ходу — каждое
  «улучшение» умножает поверхность сверки. Правила проекта это уже требуют.
- **Фаза B: страховка.** Fn-фикстуры (Mode A/B) + pinned багстейты + расширение
  replay-корпуса + выборочный DOSBox-аудит. Затем отрезание orig-слоя; судьи —
  унаследованные фикстуры и покадровые golden-хэши, снятые с последнего
  дифф-чистого барьерного прогона.
- **Фаза C: struct overlay — ключевой трюк перехода к читаемости.**
  Packed-структуры, layout-совместимые с DS (src/structs.h уже начат):
  `*(uint16_t*)(s+0x372)` → `s->obj_count` **без изменения байтового layout**.
  Читаемость появляется, а фикстуры продолжают работать без единой правки —
  они сравнивают байты, layout не менялся. Тем же способом: имена, enum'ы,
  константы, разбиение файлов.
- **Фаза D (опционально):** смена layout/архитектуры, native-структуры вместо
  эмуляции сегментов — только под защитой B–C, с маппером фикстур на новый
  layout.

Принцип: **читаемость покупается рефакторингом под тестами, а не смелой
перепиской.**

## 4. Отвергнутые альтернативы

- **«Дожать live-verify, отдельные тесты не нужны»** — не отвечает на (а) и
  фатально на (б): после отрезания orig остаёшься без верификации вообще.
- **DOSBox как основной эталон вместо m2c** — адская обвязка (скриптинг
  дебаггера, маппинг адресов, скорость), потеря всей готовой барьерной
  инфраструктуры. Рационален только как выборочный аудит (пункт 2в).
- **Формальная эквивалентность (SMT/symbolic)** — инструментов для пары
  «16-bit real-mode asm ↔ C++» практически нет; трудозатраты несоразмерны.
- **Перегенерация через Ghidra/IDA + чистка** — v2 большей частью написан, а
  вывод декомпилятора всё равно верифицировать line-by-line; выгоды нет.
- **Synthetic-тесты как фундамент** (по образцу src/rendering/test_seg003.c) —
  придуманные входы = риск нереалистичных состояний и ложной уверенности;
  допустимы только поверх реальных фикстур (края, границы), Phase 4.

## 5. Вердикт

Подход с дифференциальными тестами не просто рационален — это **недостающее
звено выбранной (правильной) стратегии**:
1. быстрая итерация при отладке функций уже сейчас (минуты → миллисекунды);
2. страховка от перезаписи replay'ев (pinned багстейты #175/#177);
3. единственный механизм, сохраняющий верифицируемость после отрезания
   orig-слоя;
4. предпосылка финального рефакторинга к идиоматичному C++ (struct overlay под
   защитой фикстур).

Лучшего пути для рукописного asm без компилятора-эталона в индустрии нет: все
успешные аналоги шли так же, но с более слабой сверкой.

Детальный дизайн тестовой инфраструктуры: см. FN_TEST_ANALYSIS.md.
